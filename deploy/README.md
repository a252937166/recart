# Deploying ReCart

This mirrors the public demo: one small Linux host, Node 22, PostgreSQL 16, nginx in front, and systemd keeping the process alive. Replace `recart.example.com` with your domain.

1. **Build** on your machine: `npm ci && npm run build`. This writes `dist/web` (static app) and `dist/server` (API).
2. **Copy the app.** Copy `dist/`, `package.json`, `package-lock.json` and `evidence/` to `/opt/recart/app`. Then run `npm ci --omit=dev` there as the service user.
3. **Database.** Any PostgreSQL 14 or later works. The demo runs it in a container bound to loopback:
   ```sh
   docker run -d --name recart-pg --restart unless-stopped -p 127.0.0.1:5435:5432 \
     -e POSTGRES_USER=recart -e POSTGRES_PASSWORD=<strong password> -e POSTGRES_DB=recart \
     -v /opt/recart/pgdata:/var/lib/postgresql/data --memory 192m postgres:16-alpine
   ```
   On old hosts with libseccomp below 2.4, add `--security-opt seccomp=unconfined`; otherwise Postgres 16 and later fail to write WAL. Migrations run automatically at startup.
4. **Configuration.** Write `/opt/recart/recart.env` from `.env.example`, with root ownership and mode 0640, readable by the service group. Set `PUBLIC_BASE_URL=https://recart.example.com`, `COOKIE_SECURE=true`, the database URL, the PayPal Sandbox app credentials, `PAYPAL_WEBHOOK_ID`, `CODEX_API_URL` with `CODEX_API_KEY` for the primary language provider, and `LANGUAGE_URL` with `LANGUAGE_TOKEN` if you deploy the hosted agent as backup. The Codex gateway answers one request at a time (measured 11–16 s per ReCart call); `CODEX_DEADLINE_SECONDS` (default 100) bounds a buyer-facing draft and `CODEX_EXPLAIN_DEADLINE_SECONDS` (150) the explanation, which runs in a background job. After a network failure the backup answers until one shared status probe reaches the gateway again; after a refusal (quota, queue, authentication) the backup answers for the full `LANGUAGE_COOLDOWN_SECONDS` (60) or the gateway's `Retry-After`, because a gateway that answers its status URL has not shown it can take requests. Refusal and network holds are kept apart and only grow, and every probe and call carries the failure generation it started in, so a result that started before a newer failure can never lift, weaken or shorten that failure's hold.
5. **Service.** Check the unit against the host's systemd first: copy it to a scratch path and run `deploy/validate-service.sh verify <path>` as root (it fails on any `systemd-analyze verify` warning about the file). Then install it into `/etc/systemd/system/`, note the local time, run `systemctl daemon-reload && systemctl enable --now recart`, and run `validate-service.sh installed "<that time>"` (effective settings, no parse warnings since the reload, stop timeout against the app's shutdown bound) and, once it is running, `validate-service.sh running` (see Logs). It listens on 127.0.0.1:4060.
6. **nginx and TLS.** Install `nginx-recart.conf`, issue a certificate (for example `certbot certonly --webroot -w /var/www/recart-acme -d recart.example.com`), run `nginx -t`, and reload nginx. `/api/events` is a server-sent event stream and `/mcp` the MCP endpoint, so both are proxied without buffering; `/v1/` accepts catalog and stock batches up to 2 MB. Every route that drafts (`/api/goal/extract`, `POST /v1/requirement-drafts`, the MCP `draft_requirements` tool) has a 180 s read timeout, above the worst case of one draft: a 5 s status probe, the primary up to `CODEX_DEADLINE_SECONDS` plus 15 s transport grace, the 15 s backup, and 5 s to record and answer (140 s with the defaults; `/api/health` reports it as `language.worstCaseSeconds`). After changing timeouts, check the effective configuration with `nginx -T`, not only the file: `/api/goal/extract` must match `location /api/`, not inherit the default location's 60 s.
7. **PayPal webhook.** Register a webhook for the Sandbox app with the payment events listed in `src/server/paypal/types.ts`, and put its ID in `PAYPAL_WEBHOOK_ID`. Point it at `https://recart.example.com/api/webhooks/paypal`, or at the hosted agent's `/v1/paypal/webhook` if PayPal does not deliver to your domain (see `hosted-agent/README.md`). Check delivery with the Sandbox webhook simulator before relying on it.
8. **Check.** `curl https://recart.example.com/api/health` should report the database, the PayPal mode and the language service. Its `build` field gives the process ID, the process start time and the SHA-256 of key modules as the running process loaded them; compare those with your fresh build (`shasum -a 256 dist/server/server/jobs/worker.js ...`) and with `systemctl show -p MainPID recart` to prove the restart picked up the new code.
9. **Client addresses and quotas.** nginx sets `X-Forwarded-For` to the real client address only (a client-sent list is dropped), and the app trusts that header from the loopback proxy alone (`TRUST_PROXY=loopback`). Set `TRUST_PROXY` to your proxy's addresses if it runs elsewhere, or `none` when clients reach the app directly. Per-address hourly quotas: `DEMO_SESSIONS_PER_HOUR` (100), `LANGUAGE_CALLS_PER_HOUR` (200) and `SANDBOX_SIGNUPS_PER_HOUR` (30); a 429 carries `Retry-After` and the reset time, and the pages show when to try again.

10. **Job lanes.** One process runs two durable job runners over the same `jobs` table: the core lane (payment operations, reconciliation, deadlines, notifications, webhooks) and the language lane (`explain_case`, which waits on the model). A lane never claims the other lane's kinds, so a slow explanation cannot delay a hold release or a refund poll. A language job's lease is the worst-case explanation time plus a minute; on shutdown each runner waits briefly, then gives any lease it still holds back so the next process resumes the job at once. An explanation job that fails for good (five attempts) settles its case: the template stays and `pending` is cleared with the error. The FAILED state and that cleanup commit in one transaction, and only the runner that still holds the lease (status `RUNNING`, lease owner itself) can make them; a runner whose lease was taken over changes nothing, and a failure after a requested rerun keeps the job retryable without settling. If the cleanup cannot be written, neither change commits and the job is handed back to run again.
11. **Controlled fault simulation.** To prove the timeouts and the failover on the live site without touching other callers, scope a fault to one demo session or one sandbox merchant from the server shell: `node dist/server/server/admin.js language-fault --scope session:<id> --fault '{"primary":{"delay_ms":70000}}' --ttl-seconds 600` (also `"outcome":"unreachable"` or `"refused"` with a `status`, a `backup` action, and `"task":"explain_change"` to target the explanation). Only that scope's calls are shaped; the shared cooldown and probes are untouched. A delay counts against the provider's own time bound, exactly like a slow real call: the real call afterwards gets only what is left of the budget, so a faulted draft can never outlast the worst case the proxy timeouts are sized for (a 70 s delay leaves the gateway 30 s, and if a busy gateway cannot fit that, the backup answers). Because scoped faults never touch shared state, they cannot exercise the shared cooldown; `tests/language/concurrency.test.ts` does, and can run against a deployed compiled tree with `RECART_IMPL_DIR=<copy of dist/server> npx vitest run tests/language/concurrency.test.ts`. `--clear` removes a fault, `--list` shows active faults, and rows expire. `tools/check-proxy-timeouts.mjs` runs the whole check (a 70 s primary, a slow failure with the backup answering, a refusal) on `/api/`, `/v1/` and `/mcp` and records the result for the evidence page.

12. **Logs.** The unit sends stdout and stderr to the systemd journal explicitly (`StandardOutput=journal`, `StandardError=journal`, `SyslogIdentifier=recart`); read them with `journalctl -u recart`, and the application's errors alone with `journalctl -u recart -p err` (the unit sets `LOG_PRIORITY_PREFIX=true`, so `console.error` and `console.warn` lines carry `<3>` and `<4>` prefixes that journald turns into priorities). Older systemd versions, such as 219 on the demo host, have no `append:` or `file:` output targets (added in 240 and 236), and the unit uses neither. On a host whose journal is volatile (no `/var/log/journal`, as on the demo host), rsyslog's imjournal copies each line to `/var/log/messages` (as `recart: ...`), which logrotate rotates weekly; that copy survives a reboot. `validate-service.sh running` proves both destinations: it finds the current process's startup line in the journal, then sends the process SIGUSR2, which writes one marked line to stdout and one to stderr, and checks that the stdout line is filed at info, the stderr line at err, and both appear in `/var/log/messages`.
13. **Shutdown.** On SIGTERM the app ends every open event stream (clients reconnect after 3 s), stops both job runners and drains HTTP at the same time: in-flight requests get `SHUTDOWN_DRAIN_SECONDS` (15) before their connections are closed, a running payment or notification job gets `SHUTDOWN_JOB_GRACE_SECONDS` (10) to finish, and a running explanation gets `SHUTDOWN_LANGUAGE_GRACE_SECONDS` (1), because a model call can last minutes and is safe to resume. A job still running after its grace has its lease handed back, so the next process takes it over at once; every job is safe to run again (payments by request ID and in-flight checks, explanations by the pending flag). The server stops accepting connections when the shutdown starts, so a restart is unreachable for the shutdown plus the new process's startup, about 2 s when no payment job is mid-call. `tools/check-restart.mjs` proves this on the live site with an open event stream and a running explanation. The process exits by itself within 25 s with the defaults, and the unit's `TimeoutStopSec=45` leaves a margin, so systemd never needs SIGKILL. `validate-service.sh installed` computes the bound with the compiled app's own `shutdownPlan` in the effective `WorkingDirectory`, including all three shutdown settings; it reads only those settings from the unit and its ordered `EnvironmentFiles`, with files overriding unit values, without executing the files or printing other environment values. It requires at least 10 s between the app's bound and the effective stop timeout, and fails if the settings or installed modules cannot be read or validated. For example, a language grace of 60 s raises the bound to 73 s and needs `TimeoutStopSec` of at least 83 s. The journal shows `SIGTERM: shutting down`, each runner's `stopped` line (with any job it handed back) and `shutdown complete in N ms`.

## Merchant platform

- **Configuration.** Set `RELEASE_ID` (shown in `/api/health` and the footer). Optionally set `SANDBOX_SIGNUP`, `SANDBOX_TTL_HOURS` and `SANDBOX_SIGNUPS_PER_HOUR` for self-serve sandbox stores. Migrations, including the platform tables, run at startup; back up the database first (`docker exec recart-pg pg_dump -U recart recart | gzip > backup.sql.gz`).
- **Operator merchants.** Create one with a key limited to what its integration needs; the key is printed once:
  ```sh
  sudo -u recart bash -c 'set -a; . /opt/recart/recart.env; set +a; /usr/local/bin/node dist/server/server/admin.js create-operator \
    --name "Your store" --tax-rate-bps 800 --max-age-seconds 7200 --label "catalog sync" \
    --scopes catalog:read,catalog:write,recoveries:read,recoveries:write,events:read,settings:write'
  ```
  List its ID in `REFERENCE_MERCHANT_IDS` to show its aggregate integration status on `/merchants`.
- **Shopify reference sync (optional).** Copy `examples/shopify-sync/` to `/opt/recart/shopify-sync`. Write `/opt/recart/shopify-sync.env` (root:recart, 0640) with `RECART_BASE_URL=http://127.0.0.1:4060`, the operator key and the Shopify app credentials. Then install `recart-shopify-sync.service` and enable it. It runs `watch --include-drafts --interval 60` and logs to the journal (`journalctl -u recart-shopify-sync`).
- **Check.** `curl https://recart.example.com/v1/capabilities` lists the features, and `/api/integrations/reference` shows the reference integration's health.
